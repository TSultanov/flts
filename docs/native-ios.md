# Native iOS app (iPhone and iPad)

The SwiftUI app in `native/` also builds for iOS, as the `FLTS-iOS` target of
`native/FLTS.xcodeproj` (generated from `native/project.yml`). It shares the
macOS app's sources; see `docs/native-macos.md` for the architecture, the Rust
core and the bindings. It replaces the Tauri iOS app: same bundle id
(`com.TS.FLTS`), same data directory inside the app's container, the same
version with a higher build number (101 against the Tauri app's 100), so
installing it over the Tauri app keeps the library, settings and sync
identity. It needs iOS 18; the Tauri app ran on iOS 15.

## What differs from macOS

- **App shell** (`App/FLTSApp+iOS.swift`): one window group with a navigation
  stack. Settings is a sheet with a page per section instead of a Settings
  window; there are no menus. Coming back to the foreground wakes sync.
- **Reader input** (`Reader/ReaderCanvas+iOS.swift`): a tap selects a word and
  shows its translation (a near miss still counts: short words are narrower
  than a fingertip), a swipe turns one spread, a tap in the margin turns the
  page, a long press opens a menu (Look Up, Copy Word/Sentence/Paragraph,
  Translate). A hardware keyboard pages with the arrow keys and Space; W and
  C toggle the word details and the chapter list. For those keys the reader
  is the first responder, with an empty input view: without one, the software
  keyboard came up whenever a menu opened. (Shortcuts on views, app commands
  and the app delegate did not receive plain keys reliably.) ⌘ shortcuts are
  app commands. Text size and appearance are in the reader's toolbar menu. Layout, paging, drawing and hit testing are
  the shared `ReaderCanvas`.
- **Layout**: two pages side by side when the reader is wide enough (an iPad
  in landscape), one otherwise. At compact width (an iPhone, or an iPad in a
  narrow split) the word's details stack in one column.
- **iOS only**: the system dictionary for the selected word, and scanning
  another device's pairing code with the camera (hidden where the camera
  scanner is unsupported, as in the Simulator).
- **macOS only**: Lyrics and the Spotify settings (they read the desktop
  Spotify client), Reveal in Finder.

## Build

`native/scripts/build-core.sh <profile> ios|ios-sim` builds the Rust core for
devices or the Simulator into `native/build/core-ios` and
`native/build/core-ios-sim`; Xcode runs it as a build phase. The Swift
bindings are the same on every platform and are generated by the macOS build.

A device build needs signing with the team in `project.yml`; build and
install it from Xcode (scheme `FLTS-iOS`) or with `xcodebuild`. An unsigned
device build (`CODE_SIGNING_ALLOWED=NO`) compiles and links.

## Tests

All of these run in a Simulator, headless, on a fresh copy of the library that
`make test-macos-native-ui` seeds (run that once first). The app reads its
library from a host folder through `FLTS_CONFIG_DIR`.

- `make test-ios-native-ui` (about 60 s plus the build): a tour of the
  library, reader, word details, landscape, chapters, Settings, import and
  onboarding. `SIM=<simulator id> NAME=<label>` picks a simulator; the
  default is an iPad. Screenshots land in
  `native/build/ios-ui-run/<label>/shots`.
- `make test-ios-native-ui-services` (about 45 s plus the build): against the
  e2e sims it imports a text, translates its chapter, reads a word, translates
  the paragraph again and adds an Anki card, then moves the book into a folder
  and deletes it; and it turns sync on with the real engine kept to this
  machine.

Verified this way on an iPad Air 11-inch and an iPhone 17 (iOS 27) and an
iPhone 16e (iOS 18.4, the minimum).

`native/scripts/ios-container-check.sh` runs the path a real device takes: with
no test folder the app uses its own container. A fresh install goes through
onboarding and writes `config.json` under
`Library/Application Support/com.TS.FLTS/`, where the Tauri app keeps it; with
a library then placed there, the app lists and opens its books.

## Not verifiable in the Simulator

Installing over the Tauri app and keeping its data, the camera scanner, the
local-network permission prompt, access to files picked from other apps, and
what iOS does to sync while the app is in the background all need a real
device.
